# Анализ неровного проигрывания (рывки/заикания)

Наблюдение: MP3-декодер корректен (побитово совпадает с minimp3, корреляция 0.99999
с ffmpeg), данные в декодер приходят в темпе реального времени (счётчик кадров стабильно
~38.5 кадров/с на всём интервале). Тем не менее звук прерывается. VLC проигрывает ту же
станцию ровно и без долгой буферизации, проигрыватель Windows (WMP) — с заиканиями, как
и наш плеер.

Важно: проблема распадается на **два уровня**, которые нужно различать:

- **Уровень данных** — сервер → сокет → кольцевой буфер → декодер;
- **Уровень воспроизведения** — декодер → waveOut-очередь → звуковое устройство.

Счётчик кадров (декодер в реальном времени) говорит, что у нас уровень данных в целом
справляется (в отличие от WMP, у которого буфер меньше и он «голодает»), но остаётся
проблема на уровне воспроизведения и/или джиттера данных.

---

## Гипотезы: уровень данных (сервер → декодер)

### 1. Бурстная (рывками) отдача сервера — **наиболее вероятная на этом уровне**
Сервер отдаёт данные неравномерно: быстро выдаёт порцию, затем пауза. Средняя скорость
может быть равна реальному времени, но мгновенная — скачет.

- Следствие: нужен буфер, способный поглотить «рывок» целиком.
- У нас: кольцевой буфер 1 МБ + пребуфер 8 с. Но кольцевой буфер наполняется только
  «излишком» скорости (во время рывка) и медленно расходуется в паузах; при старте он
  почти пуст (его опустошали в пребуфер).
- VLC: ставит большой/адаптивный сетевой буфер (входной кэш), сглаживающий рывки.

**Проверка:** логировать мгновенную скорость приёма (байт/с) с малым окном (например,
100 мс) и смотреть на разброс.

### 2. Малый сокетный приёмный буфер (SO_RCVBUF)
По умолчанию Windows даёт небольшой приёмный буфер (десятки КБ; дальше — авто-настройка
с window scaling). Если сервер шлёт крупными порциями, окно TCP закрывается, сервер
вынужден ждать, и возникает пауза.

- VLC обычно выставляет большой `SO_RCVBUF`.
- У нас `TcpClient.ReceiveBufferSize` не задаётся явно.

**Проверка:** задать `ReceiveBufferSize = 1–2 МБ` и сравнить поведение.

### 3. Сервер отдаёт стабильно медленнее реального времени
Если источник стабильно медленнее, чем нужно для воспроизведения, ни один буфер не спасёт
навсегда — он лишь отодвигает исчерпание.

- Признак (после честного расчёта от старта проигрывания): процент реального времени
  стабильно < 100%, и запас буфера монотонно тает.
- Для `195.91.237.50:8000/ices128` это похоже на правду (та же станция с другого релея
  идёт нормально — значит, дело в конкретном сервере).

**Проверка:** долгий прогон + график заполнения буфера и скорости приёма.

### 4. Разный HTTP-запрос → разное поведение сервера
Сервер может отдавать поток по-разному в зависимости от заголовков:

- `Icy-MetaData: 1` vs `0` — влияет на вставку метаданных (и, возможно, на отдачу);
- `User-Agent` — некоторые серверы/прокси ведут себя по-разному для разных клиентов;
- HTTP/1.0 vs HTTP/1.1, `Connection: close`.

У нас: HTTP/1.0, `Icy-MetaData: 1`, `Connection: close`, `User-Agent: InternetRadio/1.0`.

**Проверка:** сравнить скорость приёма с разными комбинациями заголовков (в т.ч. с
User-Agent вида VLC).

### 5. Прочие сетевые мелочи (маловероятно)
- `TCP_NODELAY` — у нас уже `NoDelay = true` (Nagle выключен).
- Delayed ACK — маловероятная причина при потоковой передаче.

## Гипотезы: уровень воспроизведения (декодер → звук)

### 6. Джиттер пополнения звуковой очереди из-за опроса `Thread.Sleep(1)` — **наиболее вероятная**
Наш `WaveOutPlayer` пополняет waveOut-очередь, опрашивая флаг `WHDR_DONE` в цикле с
`Thread.Sleep(1)`. Гранулярность системного таймера Windows по умолчанию ~15.6 мс, поэтому
момент освобождения буфера обнаруживается с задержкой до ~15 мс, и пополнение очереди
происходит неравномерно.

- VLC использует звуковой вывод через WASAPI (или аналог) с колбэком на
  высокоприоритетном аудио-потоке (часто с MMCSS) — очередь пополняется точно по такту
  звукового устройства.
- Это объясняет, почему при «здоровом» потоке данных (счётчик кадров ровный) звук всё
  равно может прерываться.

**Проверка:** заменить опрос на событие `CALLBACK_EVENT` или корректный колбэк и сравнить.

### 7. Приоритет потока декодера
Поток декодера работает с обычным приоритетом. Если его вытесняют другие процессы/GC, он
задерживается с пополнением очереди, и при недостаточном запасе возникает провал.

- VLC поднимает приоритет аудио-потока (MMCSS — Multimedia Class Scheduler Service).

**Проверка:** `ThreadPriority.AboveNormal` на потоке декодера (и/или MMCSS) и сравнение.

### 8. Паузы сборщика мусора (GC)
Аллокации на горячем пути вызывают периодические GC-паузы, которые могут «выбивать» поток
декодера из реального времени.

- Уже устранено: переиспользование буферов `co/si` в `L3Imdct36` (~11 тыс. аллокаций/с).
- Осталось: `short[]` на каждый кадр в `DecodeAvailable` (~43 аллокации/с), мелкие массивы
  в `L3DecodeScalefactors`.

**Проверка:** профилировщик GC / убрать оставшиеся аллокации.

### 9. Расхождение тактовых частот (clock drift)
Звуковое устройство может играть чуть быстрее/медленнее 44100 Гц, а источник отдаёт
строго в реальном времени. Тогда буфер медленно дрейфует (растёт или тает). Для коротких
сессий маловероятно, но на длинных интервалах даёт постепенное накопление/исчерпание.

**Проверка:** долгий прогон, наблюдение медленного изменения заполнения буфера при
ровной скорости приёма.

## Как локализовать (диагностика)

Чтобы отделить «сервер медленный/рывками» от «проблемы воспроизведения», полезно
логировать:

1. **Мгновенную и среднюю скорость приёма** (байт/с) с малым окном — увидим бурсты и
   дефицит.
2. **Заполнение кольцевого буфера** (сколько байт накоплено) — увидим, тает ли запас.
3. **Заполнение waveOut-очереди** (сколько буферов в полёте) — увидим underrun'ы.
4. **Число underrun'ов** звуковой очереди (когда очередь опустела).

Сейчас в `play` уже есть счётчик кадров по секундам и итоговый процент реального времени
(считается от фактического старта проигрывания).

---

## Рекомендуемый порядок действий

1. **Диагностика** (п. «Как локализовать») — понять, на каком уровне проблема.
2. **Заменить опрос `Thread.Sleep(1)` на событие** (`CALLBACK_EVENT` или корректный
   колбэк) — устраняет джиттер пополнения очереди (гипотеза 6).
3. **Увеличить сетевой приёмный буфер** (`ReceiveBufferSize`) — гипотеза 2.
4. **Поднять приоритет потока декодера** — гипотеза 7.
5. Сравнить с VLC после каждого изменения.

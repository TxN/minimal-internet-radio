# Статус проекта InternetRadio

Модуль проигрывания интернет-радио на C# (netstandard2.0, без внешних зависимостей,
без привязки к Unity).

## Что реализовано и работает

### 1. Декодер MP3 (`Mp3Decoder`)
Собственный скалярный порт public-domain алгоритма [minimp3](https://github.com/lieff/minimp3) (CC0).
Поддерживается MPEG-1/2/2.5 **Layer III**: моно, стерео, Joint Stereo (M/S + intensity),
короткие блоки, битовый резервуар.

**Валидация:**
- побитово идентичен эталонному minimp3 (собран оригинальный C через tcc, `max diff = 0`);
- на 146-секундном музыкальном MP3 320 кбит/с: корреляция **0.99999999997** с ffmpeg,
  макс. расхождение **2 LSB**, отношение сигнал/ошибка **−102.7 дБ**, длина выборки
  совпадает (кадры не терялись и не дублировались);
- чистый синус декодируется с THD ≈ −95 дБ.

### 2. Стриминг (`StreamClient`, `IcySplitter`)
- сырой TCP (+TLS через SslStream), ручной разбор статус-строки `ICY 200 OK` /
  `HTTP/1.0 200 OK` и заголовков;
- разбор in-band ICY-метаданных (`StreamTitle`, UTF-8);
- **HTTP-редиректы (302)** — до 10 переходов;
- автопереподключение при обрыве.

### 3. Буферизация
- `RingBuffer` — потокобезопасный кольцевой буфер (по умолчанию 1 МБ);
- пребуфер перед стартом декодирования (по умолчанию 128 КБ ≈ 8 с аудио);
- `WaveOutPlayer` — 24 блока ~100 мс ≈ 2.4 с между декодером и звуковым устройством.

### 4. Публичный API (`InternetRadio`)
`SetUrl` / `Start` / `Stop` + события `PcmDecoded` (PCM 16 бит, interleaved),
`StreamTitleChanged`, `StateChanged`, `Error`. Кроссплатформенный, без Unity-зависимостей.

### 5. Подключаемые декодеры (сделано)
- `IAudioDecoderFactory` — публичный контракт плагина: `CanDecodeContentType` +
  `CanDecodeMagic` (самодостаточный детект, без internal-типов ядра),
  `UsesIcyMetadata` (политика in-band метаданных: контейнерные кодеки возвращают
  `false`), `Name`, `Create`. Свой экземпляр передаётся через
  `radio.Decoders.Register(...)`.
- `AudioDecoderRegistry` — упорядоченный набор фабрик, два прохода детекта
  (`Content-Type` побеждает сигнатуру), `Register(..., replaceExisting)`,
  `Unregister`, `Names`, `CreateDefault()`. При отсутствии подходящего декодера —
  `NotSupportedException` с перечнем зарегистрированных кодеков, Content-Type и
  hex-префиксом потока.
- `Mp3DecoderFactory` (публичная) регистрируется в `CreateDefault()`; сам
  `Mp3Decoder` остался internal и создаётся только через фабрику.
- `CodecDetector` / `StreamCodec` удалены: единственный источник правды о сигнатурах —
  фабрики (заодно это рабочий образец для внешнего плагина).
- Окно детекта — 1 КБ. Накопленный префикс **переигрывается** декодеру, поэтому
  заголовки контейнера и ID3v2-тег не теряются (для Ogg это критично: без
  идентификационного заголовка декодер не инициализируется).
- Фабрика MP3 пропускает ведущий ID3v2-тег (syncsafe-размер + флаг футера), если он
  укладывается в окно детекта; тег больше окна требует явного `Content-Type`.

### 6. Исправления в пайплайне (сделано)
- **Реконнект.** Читатель инкрементирует счётчик эпохи соединения сразу после
  успешного `Connect`, до записи первых байт нового потока. Декодер при смене эпохи
  пересоздаётся, `IcySplitter` сбрасывается с учётом `UsesIcyMetadata`, пребуфер
  набирается заново. Ранее `IAudioDecoder.Reset()` не вызывался вообще, а
  `IcySplitter.Reset()` — один раз за сессию, поэтому после обрыва сплиттер продолжал
  счёт с середины интервала и метаданные (а для контейнеров и весь битстрим) ломались.
- `_station` публикуется читателем как `volatile`-снапшот (было: незащищённая запись
  в поле, читаемое другим потоком).
- `Station.SampleRate` дополняется первым декодированным кадром, если сервер не
  прислал `icy-sr` (нужно для Ogg-потоков, где ICY-заголовков метаданных нет).
- `IcySplitter` не применяется к кодекам с `UsesIcyMetadata = false`: вырезание
  `icy-metaint` из середины Ogg-страницы разрушило бы поток.
- **Диагностика ошибок соединения.** Ошибка чтения заголовков сопровождается URL, на
  котором она возникла, числом редиректов и исходным адресом: без этого неудачный
  последний хоп цепочки редиректов читается как «исходный адрес мёртв».

### 7. Тестовый плеер (`tests/InternetRadio.Tests`)
- `decode <file> <pcm>` — офлайн-декодирование файла (кодек выбирает реестр);
- `chunk <file> <pcm> <размер>` — то же порциями (регресс-тест потокового пути:
  результат обязан совпадать с `decode`);
- `pipe <file> <pcm> [размер чтения]` — весь конвейер (кольцевой буфер → пребуфер →
  декодер) с реальными потоками; результат обязан побайтово совпадать с `decode`;
- `registry` — офлайн-проверки реестра: приоритет Content-Type над сигнатурой, порядок
  регистрации, дубликаты, `replaceExisting`, `Unregister`, диагностика, приём плагина;
- `live <url> <сек> <wav>` — запись потока в WAV;
- `play <url> <сек>` — живое проигрывание на Windows (waveOut/winmm) + диагностика;
- `wavplay <file.wav> [сек]` — проигрывание локального WAV тем же плеером (изоляция
  уровня воспроизведения от сети/декодера; логирует позицию устройства `waveOutGetPosition`
  и дрейф позиции относительно настенных часов);
- `fileplay <file> [сек]` — проигрывание локального файла в режиме стриминга:
  файл читается порциями → `RingBuffer` → пребуфер → декодер → `WaveOutPlayer`
  (тот же конвейер, что и `play`, но без сети и ICY-метаданных);
- `bench <file> [итераций] [chunkBytes]` — бенчмарк декодера на реальном файле:
  пропускная способность (МиБ/с), realtime-фактор и аллокации на проход.

Файловые команды определяют кодек через тот же реестр: `Content-Type` выводится из
расширения файла (у командной строки нет HTTP-заголовков), затем работает сигнатура.
`FileStreamPlayer` тоже переведён на реестр, поэтому `fileplay`/`pipe` работают с любым
зарегистрированным кодеком.

### 8. Валидация фазы «инфраструктура»
- Сборка: 0 ошибок.
- `registry`: 14 проверок пройдено.
- Регресс MP3 (файл 4,12 МиБ, 270 с, 44,1 кГц, стерео): `decode`, `chunk 8192`,
  `chunk 1000`, `pipe 16384`, `pipe 777`, а также два сигнатурных прогона без
  Content-Type (исходный 127-байтный ID3-тег и синтетический 20-байтный) дали
  одинаковый SHA256 `1920E5C9265E671679C6A0845B2AF4FE30174C4A89BA9134468466935997E03F`
  (23 827 968 сэмплов) — регресса нет, префикс детекта не теряется.
- `bench` 8192 B: alloc/pass 40 B (как в базлайне), медиана 559,5 мс против 581,1 мс до
  правок (в пределах шума; сам декодер не менялся).
- Живой реконнект: локальный ICY-сервер с `icy-metaint: 8192` и принудительным обрывом
  каждые 196 608 байт. Три соединения подряд дали `Buffering → TITLE: Local round N →
  Playing` на каждом, 3 239 424 сэмпла, без исключений, зависаний и потери потока.
  Это прямая проверка фикса: без сброса сплиттера метаданные после обрыва не парсились.
- Ogg-станция (`https://fallout.fm:8444/falloutfm6.ogg`) даёт ожидаемую диагностику
  `Content-Type: application/ogg, leading bytes: 4f 67 67 53 00 02 00 00` — слот под
  плагин работает, HTTPS/TLS к этому хосту проходит.

Проверено на живой станции `http://195.91.237.50:8000/ices128` — Icecast 2.4.4,
`icy-name: Staroe Radio`, MP3 128 кбит/с, `icy-metaint: 16000`: поток декодируется,
`StreamTitle` парсится (1 350 144 сэмпла за 12 с, 44.1 кГц, стерео). Остальные живые
прогоны — на локальном ICY-сервере (реконнект) и на fallout.fm (слот под Ogg).

### 9. Ogg Vorbis (фаза 2, сделано)

Плагин `src/InternetRadio.OggVorbis` — отдельная сборка (ссылается на ядро, не наоборот),
поэтому Ogg можно не подключать к проекту вовсе.

- `OggVorbisDecoderFactory` — детект по `Content-Type` (`*vorbis*`) и по сигнатуре
  (Ogg-страница, первый пакет которой — id-заголовок `0x01 "vorbis"`), `UsesIcyMetadata = false`.
  Поток `application/ogg` с полезной нагрузкой Opus не захватывается — это покрыто проверкой.
- `OggVorbisDecoder` — адаптер push→`Feed`: окно неполных пакетов с компактированием,
  ресинк по началу следующего логического потока (`OggS` с флагом BOS, с гарантированным
  продвижением, чтобы окно не росло на битом потоке), **поддержка chained-потоков**
  (см. ниже), конверсия planar float → interleaved 16 бит с усечением, буферы кадров
  переиспользуются по размеру блока. Реализует также `IAudioTagSource` — отдаёт теги
  Vorbis comment.
- `Vendored.StbVorbis` — вендоренный public-domain порт `stb_vorbis` v1.22
  (StbVorbisSharp 1.22.4), используется как есть; переименованы пространства имён и
  сужена видимость. `AllowUnsafeBlocks` включён только в этой сборке; нативных
  зависимостей нет (`Marshal.AllocHGlobal` — аллокатор рантайма).

**Chained-потоки (важно для живого радио).** Icecast-источники чейнят новый логический
поток на каждый трек: за EOS-страницей идёт BOS-страница с новыми заголовками и тегами.
Проверено, что без обработки такой поток **обрезается** на первом стыке (декодировался
только первый поток). Теперь страница начала нового потока никогда не подаётся текущему
декодеру (окно ограничивается ею), а по исчерпании текущего потока декодер
переоткрывается на ней: читаются новые заголовки/теги и звук продолжается. Проверка:
склейка двух Ogg-файлов (48 кГц моно + 44.1 кГц моно) даёт ровно 300 952 сэмпла, и
второй поток побитово совпадает со своим эталонным PCM.

**Метаданные.** Заголовки Icecast: `icy-*` и алиасы `ice-*`, плюс `ice-audio-info`
(`bitrate` / `samplerate` / `channels`) — именно оттуда формат Ogg-потоков, у которых нет
`icy-sr`; литерал `(null)` трактуется как отсутствие значения. Теги контейнера приходят
через `IAudioTagSource`/`TagsChanged`: у fallout.fm это реальные per-track теги
(`title` / `artist` / `album` / `genre`), которые обновляются на каждом чейн-переходе;
у обычных Ogg-файлов комментариев может не быть вовсе (тогда пусто).

**Валидация (фактические результаты):**

- **Побитовое совпадение** с эталонным C: 12 активов (моно/стерео, 44.1/48/192 кГц,
  от 7.5 КБ до 216 с, включая реальный chained+tagged 2 МБ захват с fallout.fm) × команды
  `decode`, `chunk 512`, `chunk 65536`, `pipe 777`, `pipe 16384`, `file 4096`,
  `file` (синхронный API) — **84 из 84** SHA256 совпали с
  `C:\TestWorkspace\audio\ref\hashes.txt`.
- **Chained-потоки:** склейка двух потоков (48 кГц моно + 44.1 кГц моно) даёт 300 952
  сэмпла, второй поток бит-в-бит совпадает со своим эталоном. На реальном захвате
  fallout.fm (2 трека в одном файле) наш PCM тоже **побитово равен эталонному C**
  (11 800 704 сэмпла, одинаковый SHA256), то есть обработка чейнинга не расходится с
  эталоном.
- **Теги контейнера:** на том же захвате — 2 события `TagsChanged` с per-track метадатой
  (`A Wonderful Guy` → `The End Of The World`), и через плеер, и через файловый API;
  у локального файла без комментариев тегов нет (событие не поднимается).
- **ID3 больше окна детекта:** MP3 с 5 КБ ID3v2-тега и без хинта (`.bin`) декодируется
  бит-в-бит.
- **Ресинк:** файл с 17 и с 4096 байтами случайного мусора в начале декодируется
  побитово так же, как чистый (4 актива, команда `resync`).
- **`registry`**: все проверки зелёные (включая 5 проверок детекта плагина).
- **Скорость и аллокации** (`bench`): realtime-фактор **x269…x402**;
  аллокации — **62…70 КБ на открытие потока** и ноль на кадр. До кэша буферов кадров
  было 11.7 МБ мусора на проход у стерео-файла (переаллокация при чередовании длинного
  и короткого блока) — для радио 24/7 это гигабайты gen0, поэтому исправлено.
- **Живые потоки:** `https://fallout.fm:8444/falloutfm6.ogg` — 1 184 128 сэмплов за 12 с,
  44100 Гц, 2 канала, `TAGS: title='Civilizations' artist='Various Artists' album='Fall Out 3'`,
  `station: name='Fallout.FM #6' genre='Example genre' ch=2 sr=44100` (из `icy-*` и
  `ice-audio-info`); `http://195.91.237.50:8000/ices128` — `name='Staroe Radio' … br=128`.
- **Регресс MP3:** `decode`, `chunk`, `file` по-прежнему дают `1920E5C9…E03F`.

### 10. Декодирование файлов и потоков (сделано)

`AudioFileDecoder` — публичный API ядра: декодирует файл или любой forward-only поток
(сеть, `MemoryStream`) теми же декодерами, что и радио.

- Режимы: фоновый (`SetSource` + `Start` + события `PcmDecoded` / `TagsChanged` /
  `Completed` / `Error`, отмена через `Stop`) и синхронный
  (`AudioFileDecoder.DecodeAll(path|stream, onFrame, onTags)`), возвращающий число
  сэмплов.
- Потоковое чтение: буфер `ReadBufferBytes` (по умолчанию 64 КБ) + окно детекта, память
  не зависит от длины источника; `BytesRead` / `SamplesDecoded` — прогресс.
- `Completed` поднимается один раз, когда источник прочитан и все кадры отданы; `Stop`
  отменяет декодирование и `Completed` не поднимает.
- Детект кодека: хинт из расширения (`AudioContentType`) + сигнатура; окно автоматически
  расширяется до конца ведущего ID3v2-тега (до 1 МБ).
- В харнессе этому API соответствует команда `file <in> <out.pcm> [readBufferBytes]`
  (`0` → синхронный вариант); её вывод обязан побайтово совпадать с `decode`.

### 11. Метаданные станции (сделано)

- `StreamClient`: алиасы `ice-name` / `ice-genre` / `ice-url` / `ice-description` /
  `ice-bitrate`, разбор `ice-audio-info` (`bitrate`, `samplerate`, `channels`), литерал
  `(null)` = значение отсутствует.
- `StationInfo`: добавлены `Channels` и `Description`; `SampleRate`/`Channels`
  дополняются первым декодированным кадром, если сервер их не прислал.
- Теги контейнера: `AudioTags` + `IAudioTagSource` в ядре; плагин Ogg читает Vorbis
  comment. Теги доступны и в плеере (`InternetRadio.TagsChanged` / `Tags`, плюс заполнение
  пустых `Station.Name`/`Genre`), и в файловом API (`AudioFileDecoder.TagsChanged` /
  `Tags` / параметр `onTags` у `DecodeAll`) — оба пути проверены на реальном захвате с
  per-track тегами.

Как воспроизвести гейты и как обновлять вендоренную версию — `docs/ogg-vorbis-plan.md`.

## Сборка и проверка

```powershell
dotnet build InternetRadio.sln -c Release

# офлайн-проверки реестра декодеров:
dotnet run --project tests\InternetRadio.Tests -c Release -- registry

# живое проигрывание (Windows):
dotnet run --project tests\InternetRadio.Tests -c Release -- play http://195.91.237.50:8000/ices128 30

# запись в WAV:
dotnet run --project tests\InternetRadio.Tests -c Release -- live http://195.91.237.50:8000/ices128 15 out.wav
```
